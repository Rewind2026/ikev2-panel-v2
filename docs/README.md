## 文档分层

```
要部署        → 根 README（快速开始 / 部署要点 / 已知限制）
要改代码      → architecture.md（包结构 → 数据流 → 实现细节 → 调试）
              ↳ 前端两条硬边界在 §12.9（CSP / 模板转义），改模板前必读
要调接口      → API.md（鉴权模型 → 端点表）
出问题了      → TROUBLESHOOTING.md（§1-7 服务端，§8 纯前端）
要升级        → CHANGELOG.md（★ 破坏性变更都在这）
查配置项      → ../.env.example（唯一权威，文档只写要点）
```

**分层的意义**：一个问题只该有一个权威出处。配置项清单只维护一份
（在 `.env.example`），文档里指过去；版本变更只维护一份（在 CHANGELOG），
不另开 release notes 文件。

## 维护约定

**1. 文档描述代码当前状态，不是设计意图。**
`architecture.md` 里若发现与代码不符，**以代码为准并顺手改文档**。
不要写"这里本来打算…"——那是 git log 和 CHANGELOG 的事。

**2. 变更记录进 CHANGELOG.md，不新建文件。**
不要为单个 PR 建 `release-notes-xxx.md`。破坏性变更必须单独标注。

**3. 引用用相对路径**，不要写 `/opt/ikev2-panel-v2/...`（仓库换位置就全断）。

**4. 文档不重复代码。**
配置项清单以 [`.env.example`](../.env.example) 为准，architecture.md 只写要点 + 指过去。
同一个表维护两份，必然有一份是错的。

**5. 裁定"不做"的事，要连测试和文档声明一起清掉。**
本项目因此踩过坑：5 个测试文件断言了当时裁定不落地的行为，导致
`go test ./...` 编译失败（CI 的 `runner-test` stage 直接红）。
裁定记录留在 CHANGELOG，测试必须删。详见 architecture §9.3。

**6. 写"为什么这样"之前，先确认不是误判。**
本项目的 UI 审计里，4 条上报项被验证为误判（HTML 实体被当成字面文本、
输入丢失其实没丢、"完全没样式"夸大）。把误判也写进 CHANGELOG，
是为了让下一个人不用重复排查一遍 —— 但前提是**真的验证过**，
不是"看起来像"。

## 排查方法论

两条来自真机排查的规则，都是"看起来像 A 问题、实际是 B 问题"的类型。

### 判断"资源是否存在"→ 权威 API > 本地 dig/ping

`dig` 返回空**只能**说明"我这台机的递归链路拿不到"，推不出"记录不存在"。

曾据此误判"DNS 记录不存在 → DDNS 没生效 → LE 与 DDNS 循环依赖死锁"，**三条结论全错** ——
同一时刻阿里云 API 上记录一直好着，而该机递归 DNS 是坏的（连主域都解析不了）。

| 判断什么 | 用什么 |
|---------|--------|
| DNS 记录是否存在 | 阿里云 API —— 用 [`cmd/dnsq`](../cmd/dnsq)（现成工具） |
| 云上资源是否存在 | 对应云的 OpenAPI |
| 服务是否在监听 | `ss -lntp` |
| 文件是否存在 | `stat`（这两个和 `dig` 一样可信） |

### 反复重启容器调试 → 会撞 Let's Encrypt 限流

LE 每标识每小时 5 次失败授权上限。调试时每次重启都触发一次，5 次就撞满，
之后**改任何配置都没用**，只能等报文里的 `retry after`。

详见 [TROUBLESHOOTING.md](TROUBLESHOOTING.md) §3.3 / §3.4 / §4.4。
